# S06 WS resource pre-review (implementation in progress)

This is an author evidence note, not a quality score or admission. No live credentials have been used. Source: `/tmp/new-api-codex-plan-pr/tools/codex-transport`.

## Application lifetime

`src/ws.rs::websocket` acquires one of the shared 256 exchange permits and 2M permits from the 536870912-byte WS payload reservation before dialing. M is the configured decompressed complete-message limit, 1..134217728; no maximum-valid message is silently clamped. Success transfers both RAII permits to the local connection-owned session future; rejection/errors drop them immediately. Shutdown aborts the containing connection task. A duplicated UDS descriptor observes read-closed readiness during the upgraded session so caller disconnection can interrupt a pump blocked writing upstream. It does not consume bytes. HTTP handling keeps its original semantics and only the upgraded session selects this monitor.

`bridge` splits each hop, then concurrently runs two `forward` futures. Each direction reads one complete message, moves it into peer `send`, waits for flush, and only then reads its next message. Application code does not clone complete messages or allocate message queues. One hop-local queued control response belongs to tungstenite. Control frames are not forwarded. The first terminating pump drops the other; close starts a five-second deadline. Both hop streams and payload reservation are then dropped. Successful WS data types and payloads remain business-opaque.

## Library phases and retained storage

Fixed upstream forks: tungstenite `4fffad30fe373adbdcffab9545e9e9bf4f2fc19f`, tokio-tungstenite `0e5b2d73aa18dd9f0a50ee9ff199d5aef7594186`; vendored source paths preserve these crates and licenses. Narrow patches add external-HTTP-server negotiated-extension adoption, raw obs-text outgoing headers, bounded decompression/encoding buffers. Exact patch artifacts will be produced at freeze.

For each hop, `protocol/frame/mod.rs` FrameCodec owns input BytesMut and output Vec. Input assembly validates max_frame_size before `reserve(len)` and returns `split_to(len)`: a payload slice may retain a larger backing block while a tail shares it. Output `drain` removes bytes but retains capacity. Both can therefore be a history-dependent retained base even when the current message is tiny. Runtime sets frame limit F=2M+65536, write-buffer limit F, read-buffer chunk 65536, message limit M; control encoding overhead is finite. F accommodates compressed wire expansion without reducing a valid M-byte uncompressed message.

Receiving fragmented messages retains `IncompleteMessage` String/Vec <=M logical bytes, while the current frame and (if compressed) its decompressed output temporarily coexist. `protocol/mod.rs` computes remaining message limit before decompression. The patch in `extensions/compression/deflate/mod.rs` grows output geometrically but caps requested Vec capacity at remaining+1; producing that one excess byte fails. It replaces the upstream `reserve(2 * compressed_input_len)` followed by a late size check. A cfg(test)-only capacity observation and high-compression small-limit regression prove the check occurs before unbounded growth.

On complete-message return, assembly moves into Message. During peer `write`'s compression closure, input M and compressed output coexist; input is dropped when the closure returns. During frame serialization, compressed Frame and output Vec coexist; the Frame drops when serialization returns. During a blocked flush, only encoded output Vec (plus retained input/output base of both hops and opposite-direction work) remains. Assembly, compression, serialization and blocked flush for the SAME direction are mutually exclusive. Opposite directions are concurrent, and each library's historical capacities can coexist with the other direction's current transient allocation.

The earlier rough sum of every phase (about 30M/session) was an intentionally loose overestimate, NOT a deployment requirement and NOT an actual RSS measurement. Vec/Bytes growth figures describe requested capacity and implementation growth, not allocator or kernel guarantees. Final resource reviewer should use retained base plus max(current receive phase, current compress phase, current serialize phase) per direction, not sum mutually exclusive phases. Additional rustls sessions (target plus optional HTTPS proxy), zlib contexts, allocator/kernel buffers, HTTP exchanges and runtime overhead remain outside application reservation. No 512MiB RSS bound is claimed; deployment sizing requires actual isolated evidence and will not be set from the overestimate.
